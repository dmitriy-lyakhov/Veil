# Связи между сетями: client-to-client, client-to-site, site-to-site

Сервер Veil работает как хаб: все участники подключены к нему, и он решает, какой трафик пропускать между ними.

- **Клиент** — любое устройство с туннелем Veil (адрес из подсети туннеля, `10.66.0.0/24` и ULA `/64`).
- **Сайт** — локальная сеть за **клиентом-шлюзом**: роутер или сервер в офисе, на котором поднят туннель
  в режиме шлюза. Её подсети задаются у этого клиента на сервере («Сети за клиентом»).

| Связь | Что разрешает |
|---|---|
| Клиент ↔ клиент | устройства VPN видят друг друга по адресам туннеля |
| Клиент ↔ сайт | устройства VPN попадают в сети за шлюзами, а хосты этих сетей — к устройствам VPN |
| Сайт ↔ сайт | сети за разными шлюзами связаны между собой (офис ↔ офис) |

По умолчанию разрешено всё (как было до появления настройки). Установленные соединения не рвутся
при выключении связи — запрещаются только новые.

## Настройка

1. **Шлюз сайта.** Выдайте клиента для роутера/сервера в офисе и подключите его в режиме шлюза (Linux):

   ```bash
   veil import <ссылка veil://…> office
   sudo veil connect -gateway office
   ```

   Режим шлюза включает пересылку IPv4/IPv6 и разрешает её через интерфейс туннеля. NAT не делается:
   адреса офисной сети видны на другой стороне как есть.

2. **Сети за клиентом.** В приложении: страница клиента в списке пользователей сервера → «Сети за клиентом (site)»;
   в админ-панели: клиент → «Изменить» → «Сети за клиентом (site)». По одной подсети в строке, например
   `192.168.1.0/24`. IPv6-подсети тоже можно.

3. **Связи.** В приложении: страница сервера → карточка «Связи между сетями»; в админ-панели — блок
   «Связи между сетями». Отметьте нужные связи и сохраните.

4. **Маршруты в офисной сети.** Хосты сайта должны отправлять трафик к подсети туннеля и к другим сайтам через
   шлюз: проще всего, если шлюз — их маршрутизатор по умолчанию; иначе добавьте маршруты
   (`10.66.0.0/24` и подсети других сайтов → адрес шлюза в локальной сети).

## Как это устроено на сервере

- Подсети шлюза добавляются к его `allowed_ip` в WireGuard: сервер принимает от шлюза пакеты с адресами офиса
  и отправляет ему пакеты для офиса.
- Маршруты `подсеть → TUN` (`ip route replace … dev veil0`).
- Правила пересылки TUN → TUN — цепочка `VEIL-LINKS` (iptables/ip6tables) или таблица `inet veil` (nftables):
  разрешить/запретить по парам «туннель/сайт → туннель/сайт» согласно настройке.
- Выход сайтов в интернет через сервер — маскарадинг в цепочке `VEIL-SITES`.
- Заблокированный или удалённый клиент — и его сети тоже: маршруты и правила пересчитываются сразу.

Ограничения: подсети разных шлюзов не должны пересекаться, нельзя указать маршрут по умолчанию и слишком широкие
сети (короче `/8` для IPv4, `/16` для IPv6), сети задаются на узле, к которому шлюз подключён напрямую (в каскаде —
на выходном узле). Режим шлюза — только Linux.

API (сокет управления и админ-панель): `POST settings/links {"client_to_client":…, "client_to_site":…,
"site_to_site":…}`, `POST clients/subnets {"name":…, "subnets":[…]}`; состояние — в `GET state`
(`server.links`, `clients[].subnets`).
