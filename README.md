# Veil

VPN-протокол и приложение: ядро WireGuard (Noise IK) внутри HTTPS на порту 443.
Основной транспорт — HTTP/3 (QUIC, UDP/443) с HTTP-датаграммами, запасной —
HTTP/2 поверх TLS 1.3 с отпечатком Chrome (TCP/443). Для всех, кто не знает
секретного токена, сервер — обычный сайт по обоим протоколам.

## Как это устроено

```
                                     ┌→ HTTP/3 датаграммы (RFC 9297) → QUIC → UDP/443   основной
IP-пакеты → WireGuard (wireguard-go) ┤
                                     └→ кадры в HTTP/2 POST-потоке → TLS 1.3 → TCP/443  запасной
```

- **Отпечаток Chrome везде**: HTTP/2 идёт через uTLS (ClientHello Chrome), HTTP/3 — через uquic с QUIC-пресетом Chrome 115 (ALPS, compress_certificate, `max_datagram_frame_size`, без Go-маркеров); HTTP/3-слой клиента написан поверх uquic вручную (SETTINGS, QPACK-заголовки в порядке Chrome, HTTP-датаграммы). Тест `TestH3ClientLooksLikeChrome` разбирает реальный Initial-пакет.
- **HTTP/3**: запрос `POST /api/v2/<случайный путь>`, пакеты WireGuard идут ненадёжными HTTP-датаграммами — без проблемы TCP-over-TCP. Пакеты больше текущего лимита QUIC-датаграммы режутся на фрагменты; лимит узнаётся из ответов quic-go и растёт вместе с PMTU.
- **HTTP/2**: тот же запрос, тело в обе стороны — поток кадров `[тип][длина][данные]`.
- **Padding**: первые пакеты сессии в обоих транспортах дополняются случайным мусором.
- **Alt-Svc**: TCP-сайт объявляет `h3=":443"`, как обычные сайты, поэтому QUIC на этом адресе выглядит естественно.
- **Аутентификация**: `Authorization: Bearer` — HMAC-SHA256 от времени и nonce, окно ±90 с, повтор токена отклоняется. Без валидного токена — страница сайта, 404 в стиле nginx.
- **Сертификат**: самоподписанный, клиент проверяет SHA-256 отпечаток публичного ключа (pinning). В TLS 1.3 сертификат зашифрован и наблюдателю не виден.
- **Выбор транспорта**: Happy Eyeballs по четырём вариантам с шагом 250 мс — IPv6+HTTP/3 → IPv6+HTTP/2 → IPv4+HTTP/3 → IPv4+HTTP/2, побеждает первый успешный. Если UDP режут, клиент оказывается на HTTP/2 через ~250 мс и пробует вернуться на HTTP/3 при каждой плановой смене соединения. Профиль может ограничить транспорты: `"transports": ["h2"]`.
- **Устойчивость**: обрыв TCP не рвёт WireGuard-сессию, переподключение ~100 мс; каждые 5–15 минут соединение плавно меняется на новое.
- **Внутри туннеля** — dual-stack: IPv4 `10.66.0.0/24` и случайная ULA `/64` с NAT66, весь v4/v6 трафик идёт в туннель.

## Сайт-прикрытие и админ-панель

- При установке генерируется сайт-визитка выдуманной компании (ru или en): название, род деятельности, услуги, описание, город, часы работы, логотип, одна из 6 палитр и 3 вёрсток, случайный порядок секций. Форма заявки, `robots.txt`, favicon; всё прочее — 404 в стиле nginx. Телефонов и e-mail нет — чтобы случайно не указать чужие реальные контакты.
- **Админ-панель доступна только через VPN**: `https://10.66.0.1/admin` (адрес сервера в туннеле). Снаружи `/admin` неотличим от несуществующей страницы. Внутри — вход по логину и паролю (bcrypt, блокировка IP после 5 ошибок на 15 минут, cookie `HttpOnly; Secure; SameSite=Strict`, CSRF-заголовок).
- В панели: онлайн-статус клиентов, транспорт и адрес каждой сессии, последнее рукопожатие, трафик; добавление клиента (выдаётся ссылка `veil://` и файл `.veil` — один раз, в них приватный ключ) и удаление с немедленным разрывом сессий.
- Пароль админки генерируется при первой установке и показывается в журнале установки и в карточке сервера в приложении.

## Каскад произвольной длины

- Маршрут клиента: `вход → узел 2 → … → выход`, число узлов не ограничено (проверено на 15). WireGuard-сессия сквозная от клиента до выхода, промежуточные узлы пересылают зашифрованные пакеты и не видят трафик; MTU и шифрование не растут с числом узлов.
- Каждый узел знает только своих соседей: ключ каскада (`veil-relay://`) выдаёт следующий узел предыдущему. Регистрация клиента проходит по цепочке через скрытый API на секретном пути (без ключа — 404), каждый узел выдаёт предыдущему отдельный ключ для этого клиента. Удаление тоже идёт по цепочке.
- Маршрут собирается пошагово: админка/приложение спрашивает у узла, куда он может отправить дальше.
- В приложении: «Связать со своим сервером» или «Построить каскад из нескольких серверов» — приложение само выдаёт ключи и связывает соседей по SSH.

## Автомаршрут по задержкам

- Каждый узел раз в ~30 с (со случайным разбросом) замеряет задержку до соседей обычным HTTPS-запросом и сглаживает её.
- Входной узел собирает таблицу задержек у соседей (до недоступных напрямую — через соседей), узлы опознаются по публичному ключу.
- Вход и выход фиксированы; промежуточные узлы упорядочиваются точным перебором подмножеств (до 20 узлов) с ограничением «сколько промежуточных». На случайной сетке из 15 узлов жадный «ближайший сосед» даёт путь в среднем заметно длиннее оптимального (в тесте — на 63%).
- Перестройка: если другой путь быстрее на 20% и минимум на 5 мс два замера подряд, либо сразу, если узел текущего пути пропал. Конфиг клиента не меняется: на выходе несколько путей доступа ведут к одному WireGuard-пиру с теми же адресами.

## Ближайший вход

- Профиль может содержать несколько входов и явно заданный выход. Ключ клиента генерирует приложение; каждый вход регистрирует его с маршрутом (напрямую или автоматическим) до того же выхода.
- При каждом подключении и переподключении клиент параллельно замеряет TLS-рукопожатие до всех входов и идёт через самый быстрый; недоступный вход пропускается.
- Кнопка «Перепроверить ближайший вход» показывает задержки, записывает ближайший вход в профиль и, если туннель поднят, сразу переключает его.

## Управление клиентами

Создание (с маршрутом), переименование и заметка, блокировка/разблокировка (мгновенно: заблокированный клиент не проходит аутентификацию транспорта), «новый конфиг» (перевыпуск ключей), удаление. Конфиг передаётся QR-кодом, файлом `.veil` или ссылкой `veil://`.

Приложение управляет своими серверами по SSH через локальный сокет `/run/veil/ctl.sock` (`veil-server ctl …`); веб-админка — только изнутри VPN.

## Домен

Для каждого узла можно задать домен: сайт-прикрытие открывается по нему, сертификат Let's Encrypt выпускается автоматически (TLS-ALPN-01 на 443, порт 80 не нужен). Новые клиенты и ключи каскада такого узла подключаются по домену с обычной проверкой сертификата; старые конфиги продолжают работать по IP с закреплённым сертификатом.

## Пароль админки

Меняется в веб-панели (нужен текущий пароль) или в приложении по SSH; все сессии панели при смене завершаются.

## Два способа добавить сервер

1. **Свой сервер по SSH**: IP (v6/v4), логин и пароль или SSH-ключ — приложение само ставит Veil и сайт-прикрытие.
2. **Файл или ссылка**: `.veil`-файл или ссылка `veil://…` из админ-панели. В CLI: `veil import <файл|ссылка> [название]`.

## Сборка

```
make dmg            # dist/Veil-<версия>.dmg: универсальный Veil.app (Intel + Apple Silicon, macOS 13+)
make macos-app      # только dist/Veil.app с серверными бинарниками внутри
make server app     # dist/server/veil-server-linux-{amd64,arm64}, dist/veil
go build ./cmd/veil-cli   # консольный клиент без GUI (Linux-серверы, роутеры)
make test
```

## Использование

GUI: `Добавить сервер` → IPv6 / IPv4, пользователь SSH, пароль или ключ → «Установить и подключить».
Приложение по SSH ставит `veil-server` как systemd-службу, открывает 443 в ufw/firewalld,
сохраняет профиль и поднимает туннель (запросит пароль администратора).
Повторная установка на тот же сервер добавляет новое устройство, не ломая старые.

CLI:
```
veil deploy -name ams -ipv6 2001:db8::10 -ipv4 203.0.113.10 -user root -password
sudo veil connect ams
```

## Структура

| Путь | Что |
|---|---|
| `internal/proto` | токены аутентификации, кадрирование с padding |
| `internal/streambind` | `conn.Bind` для wireguard-go поверх потоков |
| `internal/server` | TLS/HTTP/2 и HTTP/3 сервер, админ-панель, управление клиентами, NAT |
| `internal/site` | генератор сайта-визитки |
| `internal/client` | uTLS + HTTP/2, uquic + HTTP/3, Happy Eyeballs, туннель, маршруты/DNS (macOS, Linux) |
| `internal/deploy` | установка сервера по SSH |
| `internal/helper` | привилегированный процесс туннеля и управление им |
| `internal/gui` | интерфейс на Fyne: тёмная тема, большая кнопка подключения, вкладки снизу |
| `internal/config` | профили и формат ссылок `veil://` |
| `internal/e2e` | сквозные тесты; `live_test.go` — против развёрнутого сервера |

## Статус платформ

| Платформа | GUI | Системный туннель |
|---|---|---|
| macOS | есть | есть (utun, маршруты, DNS через networksetup) |
| Linux | есть | есть (TUN, ip route, resolvectl) |
| Windows | собирается | нет (нужен Wintun) |
| Android / iOS | Fyne поддерживает | нет (нужны VpnService / NetworkExtension) |
